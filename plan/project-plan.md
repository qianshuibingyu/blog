# 个人技术知识库与智能问答平台：项目阶段规划

## 1. 项目定位

本项目是一个面向个人技术内容沉淀、审核、阅读和检索的知识库平台，具备用户投稿、管理员审核、文章评论和基于文章内容的 AI 问答能力。

核心业务链路：

```text
管理员创建测试账号，用户登录
  -> 创建自己的文章并提交审核
      -> 管理员审核通过
          -> embedding 成功并写入 Chroma
              -> 通过公开门禁后展示
                  -> 登录用户发表评论
                      -> 管理员审核评论
                          -> 通过后公开
                              -> 用户提出问题
                                  -> 检索相关内容
                                      -> GPT 生成带来源的回答
```

匿名用户只能阅读公开文章和评论；普通用户登录后投稿和发表评论，但不能审核。管理员通过 Django Admin 审核所有文章和评论，并处理索引失败。

项目开发采用阶段化方式。每个阶段都有独立目标和验收标准，前一阶段完成后再进入下一阶段，避免第一版范围失控。

## 2. 总体技术选型

完整的组件、架构、技术栈、数据流、API、安全和技术能力规范统一维护在[项目开发规范](../docs/development-specification.md)。本文件只保留阶段路线和技术决策摘要。

Phase 1 技术子集：

- 后端：Python、Django、Django REST Framework
- 前端：Vue 3、Vite、Vue Router、Axios
- 数据库：SQLite，使用 Django migrations
- 认证：Django Session/Cookie + CSRF，测试账号由管理员或后端命令创建，Phase 1 不做公开注册
- 权限：Django Groups、Model Permissions 和服务端对象级 owner/admin 校验
- 编辑器：Markdown 原文存储和安全渲染
- AI：OpenAI-compatible SDK 用于聊天回答；本地 SentenceTransformers 用于 embedding、相似度检索和来源引用
- 向量存储：Chroma PersistentClient
- 测试：pytest、pytest-django，包含越权和审核状态测试
- 日志：Python logging / Django logging
- 配置：`.env` 和 `.env.example`

Phase 1 的 embedding 默认使用 `BAAI/bge-small-zh-v1.5`，由 `sentence-transformers` 在本地加载并生成 512 维向量。`MODEL_NAME` 只负责聊天模型，`EMBEDDING_MODEL` 负责向量模型，二者不能混用；文章入库和问题查询必须使用同一个 embedding 模型。

Phase 1 暂不强制引入 Pinia、Redis、RabbitMQ、Elasticsearch、Celery、Kubernetes、微服务或完整 Docker Compose。Docker Compose 是后续工程化能力，不是 Phase 1 核心完成门槛。

### 目标

完成以下最小闭环：

```text
测试账号登录
  -> 创建自己的 Markdown 文章并提交审核
      -> 管理员通过
          -> embedding 和 Chroma 均成功
              -> 统一公开门禁通过后展示
                  -> 用户阅读和评论
                      -> 用户提问并获得引用来源
```

### 功能范围

- 登录、退出和当前用户信息；不做公开注册
- 普通用户创建、编辑草稿、删除自己的文章；发布后通过删除旧文章再创建新草稿替代编辑
- 文章草稿、待审核、索引中、索引失败、公开、下架和硬删除状态
- 管理员审核、通过、驳回、下架和删除任意文章
- Markdown 编辑和安全渲染
- 登录用户创建、删除自己的评论；评论提交后不提供普通用户编辑
- 管理员审核、下架和删除任意评论
- 公开文章列表、详情和已通过评论
- 只有审核通过、embedding 成功且 Chroma 写入成功的文章建立有效索引并公开
- 审核结果站内通知；索引失败只通知管理员并支持 Admin/管理命令重建
- 单轮 AI 问答、来源片段和异常提示
- 对象级权限、审核审计和越权测试

### 明确排除

- 复杂分页、高级搜索和复杂分类标签页面
- 点赞、收藏、邮件/短信通知、订阅和推荐（站内审核结果通知除外）
- 多轮对话、流式输出和 Agent 工具调用
- Celery、Chroma HTTP Server、Redis 和高并发部署
- 完整 Docker Compose 交付
- AI 自动发布或绕过审核覆盖原文

### 完成标准

- 测试用户可以登录、投稿和管理自己的文章；不实现注册
- 普通用户不能编辑、删除或审核他人文章和评论
- 管理员可以管理账号，并审核、下架和删除所有文章与评论
- 只有审核通过、embedding 成功且 Chroma 写入成功的文章对外公开并参与 RAG
- 前台只能查看公开文章和已通过评论
- 用户可以针对公开文章内容提问并获得来源
- 模型、索引、认证和权限异常有明确提示；技术索引错误反馈管理员，审核结果通过站内通知反馈作者
- README 可以说明安装、配置、运行和测试方法
- Docker Compose 作为可选工程化能力，不作为 Phase 1 核心完成门槛

详细范围以 [phase1-mvp.md](./phase1-mvp.md) 为准。

## 5. Phase 2：内容智能化

### 进入条件

- Phase 1 的文章管理和单轮问答流程稳定
- 已有不少于 5 篇真实技术文章
- 已能记录模型调用错误并在前端展示失败状态

### 功能范围

- AI 生成文章摘要
- AI 推荐文章标签
- AI 文章润色
- AI 生成文章标题
- AI 根据用户确认生成草稿
- 编辑页面展示 AI 生成结果

### 重点学习

- Prompt 设计
- 结构化输出
- 生成结果校验
- 用户确认后保存
- 模型调用失败的基础处理
- 上下文长度控制

### 完成标准

- AI 结果不能直接覆盖用户原文
- 用户可以预览、修改和确认生成内容
- 模型返回格式异常时不会破坏文章数据
- 不同 AI 功能有清晰的接口边界

Phase 2 只关注内容生产能力，不负责完整的 RAG 评估、监控、限流、备份和 CI，这些属于 Phase 4。

## 6. Phase 3：Agent 工作流

### 进入条件

- Phase 1 的 RAG 检索质量达到可用标准
- Phase 1 至少准备 20 条手工验证问题，其中包含有答案问题和无答案问题
- 在验证集上，Top-3 检索命中率达到至少 80%：问题对应的正确文章或相关片段出现在前 3 个结果中
- 有答案问题的来源引用正确率达到至少 80%
- 无答案问题不会被系统强行返回无关文章
- Phase 2 的模型调用封装稳定
- 已有明确的工具使用场景

这里的“命中”定义为：检索结果前 3 条中至少有 1 条能够直接支持问题答案的文章片段。验证结果记录在阶段文档或测试数据文件中，不凭主观感受判断。

### 功能范围

首版 Agent 只提供受限工具：

```text
search_articles(keyword)
get_article(article_id)
create_draft(title, content)
```

Agent 可以：

- 根据问题搜索文章
- 读取指定文章
- 汇总多篇文章
- 根据检索内容生成文章草稿
- 将草稿保存为待确认状态

### 安全边界

- 工具必须使用白名单
- 限制最大工具调用次数
- 不允许执行任意代码或 Shell 命令
- 不允许直接删除文章
- 草稿必须经过用户确认后发布
- 处理文章中的提示词注入内容

### 重点学习

- Tool Calling
- Agent 状态管理
- 工作流编排
- LangGraph 或等价方案
- 工具错误处理
- Agent 过程日志

### 完成标准

- Agent 只能调用白名单工具
- 正常问题可以完成检索、读取和回答流程
- 工具调用失败时能够停止并返回明确错误
- 单次请求最多调用工具 3 次
- Agent 生成的草稿必须经过用户确认后才能保存或发布
- 至少准备 10 条 Agent 场景用例，成功完成率达到 80%

## 10. 学习方式

本项目不采用先完整学习某个框架、再开始开发的方式，而采用任务驱动学习：

```text
确定当天功能
  -> 了解完成该功能所需的最小知识
      -> 让 AI 辅助解释和生成小模块
          -> 运行、修改和测试
              -> 总结已经掌握的知识
```

学习的验收标准不是看完多少教程，而是能否用当天学到的知识完成一个可运行功能，并解释它的核心数据流。

每个学习内容都必须绑定实际产出，例如：

- 学 Vue 组件：产出登录页或文章列表页
- 学 Vue Router：产出登录页和管理页之间的跳转
- 学 Axios：产出一个能调用 Django API 的页面
- 学 Django Model：产出 Article 数据表和迁移
- 学 DRF Serializer：产出文章参数校验
- 学 Django View：产出文章 CRUD 接口
- 学 Chroma：产出一篇已发布文章的可检索索引

不单独安排“把 Vue 或 Django 系统学完”的任务。遇到暂时用不到的知识，记录到后续学习清单，不影响当前功能开发。

## 11. 调研结论与技术决策

### 11.1 为什么从零开发

本项目选择从零开发，而不是直接二次修改完整开源博客，原因是：

- 可以明确理解前后端、数据库和 AI 处理链路
- 可以自主控制项目范围和代码结构
- 方便在面试中解释关键设计和实现细节
- 可以围绕 AI 知识库问答设计业务，而不是被原项目功能牵引

开发过程中可以参考开源项目的目录结构、接口设计和成熟实现，但不直接复制无法解释的核心代码。

### 11.2 为什么选择 Django + Vue

Django 提供 ORM、认证、数据库迁移和成熟的 Web 项目结构，适合第一次学习后端框架。Django REST Framework 用于建立清晰的前后端 API 边界。

Vue 3 和 Vite 的学习成本相对可控，适合在短周期内完成前台、管理端和 AI 问答页面。Vue 的组件、响应式数据、路由和 Axios 也能覆盖本项目需要的前端知识。

Python 同时适合 Web 开发和 AI 应用开发，可以避免后续再切换语言实现 RAG 和 Agent。

### 11.3 中间件取舍

调研报告中提到的 Redis、消息队列、Elasticsearch、OSS、CDN、监控平台等，属于真实线上系统可能使用的组件，但不是当前个人项目的必要条件。

当前决策：

- SQLite：优先降低开发和学习成本
- Chroma：优先完成 RAG，避免首版引入复杂向量基础设施
- Docker Compose：用于复现本地运行环境
- logging：满足基础错误排查

后续只有在明确出现性能、任务异步或数据规模问题时，才引入 Redis、Celery 或其他基础设施。

### 11.4 安全和性能边界

当前基础版本必须做到：

- API Key 只保存在后端环境变量
- 使用 ORM 和参数化查询
- Markdown 渲染进行 XSS 风险控制
- 管理接口进行登录校验
- 模型调用设置超时和错误处理
- Agent 后续使用工具白名单

当前版本不承诺 100 QPS、高并发、读写分离和多实例部署，目标是业务流程稳定、数据流清晰和代码可维护。

### 11.5 调研中的开源项目如何使用

Aurora、NBlog、Plumemo、OneBlog 和 Ghost 可以作为架构和功能参考，但不作为本项目的代码基础。

其中大型项目适合观察完整功能和中间件组合，轻量项目适合比较目录组织和接口设计。本项目最终以自己的 Django + Vue 代码为主，避免因开源项目技术栈和业务范围过重而影响学习效果。

### 11.6 主要风险和处理方式

| 风险 | 处理方式 |
| --- | --- |
| 第一次学习 Vue 和 Django，进度较慢 | 按功能纵向开发，每次只学习当前需要的框架知识 |
| AI 生成代码无法理解 | 先要求 AI 解释设计，再生成小模块，并补测试 |
| 一周内功能过多 | 保留文章发布、索引和单轮问答，其他功能降级 |
| RAG 检索效果不稳定 | 使用少量高质量技术文章，返回来源片段，先保证可解释 |
| 模型服务不可用 | 增加超时、异常提示和本地测试数据 |
| 本地 embedding 首次下载较慢或 CPU 推理较慢 | 首次运行允许下载和缓存；不提交模型文件，自动化测试使用 FakeClient |
| embedding 模型切换后旧索引维度或语义不一致 | 将模型配置变更视为索引失效，重建 Chroma 索引 |
| Docker 或数据库配置占用时间 | 先使用 SQLite 本地运行，最后再完成容器化 |

## 12. 风险分层决策

调研中发现的风险不全部推迟到 Phase 2。判断标准是：如果不处理会导致当前版本无法使用，就必须纳入 Phase 1；如果只是性能、可扩展性或自动化增强，则放入后续阶段。

### Phase 1 必须处理

- Django Session + Vue 分离场景的 CSRF、CORS、Cookie 配置
- Chroma 嵌入式模式的单进程运行限制
- embedding 调用的批量、超时、基础重试和错误日志
- 文章片段的 overlap、代码块和 Markdown 基础处理
- 入库和提问必须使用同一个 embedding 模型
- 相似度阈值和最大上下文片段数量
- 模型调用失败、超时、无检索结果时的前后端提示
- `ArticleChunk(article_id, chunk_index)` 唯一约束
- API Key 和模型配置的环境变量隔离
- RAG 手工验证用例和核心接口测试

### Phase 2 再处理

- Celery 异步建立和更新索引
- Chroma HTTP Server 独立服务
- Redis 缓存
- RAG 自动评估数据集和召回指标
- 更复杂的限流、重试队列和任务状态查询
- PostgreSQL + pgvector
- 完整 Docker 多服务部署和生产监控

Phase 1 的同步索引和本地 Chroma 属于已知技术债务，但在文档中明确记录，不伪装成适合高并发生产环境的方案。
